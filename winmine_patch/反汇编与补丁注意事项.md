# winmine.exe 反汇编与补丁注意事项

本文档记录对本目录 `winmine.exe`（Windows XP 扫雷 5.1.2600.0）做静态补丁、把棋盘上限从 **30×24** 提升到 **62×62** 过程中确认的事实、踩过的坑和验证方法。

## 目录说明

| 文件 | 作用 |
|---|---|
| `winmine.exe` | 原始目标程序，只读，不修改 |
| `patch_winmine_bigboard.py` | 生成补丁版 exe 的脚本，所有补丁为等长替换 |
| `winmine_bigbrd.exe` | 补丁版输出，最大 62×62 |
| `verify_runtime.py` | 运行时验证脚本（读内存 + 模拟点击） |
| `反汇编与补丁注意事项.md` | 本文档 |

重新生成与验证：

```powershell
cd d:\workspace\coding\mixed\superMinesweeper\winmine_patch
python patch_winmine_bigboard.py   # 需要 capstone、pefile
python verify_runtime.py           # 会在 HKCU 写配置，结束时自动恢复
```

## 三、反汇编注意事项（踩坑记录）

1. **必须开启 `md.skipdata = True`。**
   `.text` 里夹着数据，线性反汇编若不跳过数据只会得到 93 条指令；开启后得到 5423 条。被跳过的数据会生成 `id == 0` 的伪指令，遍历时要 `if ins.id == 0: continue`，否则访问 `operands` 会抛 `CS_ERR_SKIPDATA`。

2. **不要依赖 `ins.encoding`。**
   当前环境安装的 capstone 版本没有 `ins.encoding`，访问会 `AttributeError`。定位立即数的可行做法：
   - imm8：直接看指令字节的**最后一个字节**；
   - imm32：在该指令 `ins.bytes` 中搜索 4 字节旧常量的唯一出现位置。

3. **等长替换是硬约束。**
   没有重定位表、`.text` 内也没有现成代码洞，改动指令长度会破坏后续硬编码的跳转偏移。因此只做同长度改写：
   - `shl r32, 5` → `shl r32, 6`（`C1 E0 05` → `C1 E0 06`，改末字节）；
   - `add/sub r32, 0x20` → `0x40`（`83 C0/... 20`，改末字节）；
   - `push 0x18` → `push 0x3E`（`6A imm8`，改末字节）；
   - `mov eax, 0x360` → `0x1000`（`B8 imm32`，改偏移 1 开始的 4 字节）；
   - 内存操作数里的绝对地址：在指令字节内替换 4 字节立即数。

4. **改 imm8 前必须校验末字节。**
   同一助记符可能对应不同编码。例如 `add esp,0x20` 与 `sub esp,0x20` 都是 `83 /0`/`83 /5` + imm8，如果直接把末字节从 `0x20` 改成 `0x40` 而不校验指令，可能误改函数栈帧。脚本里的 `0x10031D7 sub esp,0x20` 就**不能动**，只处理 10 处真正的跨行步长。

5. **只改棋盘相关的 `shl r32,5`。**
   全文件共 22 处 `SHL r32,5` 参与棋盘行索引，但其它移位（如位运算、图色处理）不能碰。补丁点必须来自对棋盘基址引用上下文的交叉确认，而不是全局替换。

6. **4 字节常量必须在单条指令内唯一。**
   替换棋盘基址时，`ins.bytes` 中若同一旧常量出现多次要报错；脚本用 `find` + 二次 `find` 校验唯一性，避免改错位置。

7. **地址常量不要写错位数。**
   曾把 `0x1005340` 误写成 `0x0105340`，导致“棋盘引用统计为 0”。写常量时统一用完整绝对地址（`0x1000000 + RVA`）。

8. **步长是 2 的幂时，只改指数。**
   `32 → 64` 只把 `shl 5` 变 `shl 6`，行步长 `0x20 → 0x40` 只改 imm8，整体长度不变，是方案 B 成立的关键。

9. **方案 C（128 步长 / 更大尺寸）会破坏等长前提。**
   - `add/sub reg, 0x80`：imm8 `0x80` 会被符号扩展为 −128，语义错误，必须换成 imm32 编码，指令变长；
   - `push 0xFE`（254）：imm8 同样符号扩展，宽度 254 不能用 `push imm8`；
   - 队列回绕 `cmp ...,0x100`：超出 imm8 范围，也要变长。
   一旦指令变长，必须用代码洞 / trampoline 重写并修正相对跳转，这是方案 C 的主要工作量。

## 四、手工新增 PE 节的注意事项

当前 `pefile` 版本**没有 `add_section` 方法**，只能手写节表：

1. 节表项固定 40 字节；节名是 8 字节字段。用 `bytearray(40)` 时写 `hdr[0:8] = b".bigbrd"` 只有 7 字节，会把 bytearray 缩短成 39 字节，随后 `pack_into` 报 `requires a buffer of at least 40 bytes`。**正确写法是 `hdr[0:7] = b".bigbrd"`**。
2. 追加节数据前，先把文件长度按 `FileAlignment(0x200)` 补齐；再追加对齐后的节原始数据。
3. 必须更新：
   - `NumberOfSections` +1；
   - `SizeOfImage` = 对齐(新节 RVA + VSize) → `0x22000`；
   - `SizeOfInitializedData` += 节 RawSize。
4. 新节 RVA 用“上一节 VirtualAddress + VirtualSize”按 `SectionAlignment` 对齐，并断言等于 `0x20000`；同时确认节表末尾加 40 字节仍在 `SizeOfHeaders` 范围内。
5. 新节 Characteristics 用 `0xC0000040`（initialized data + 可读写）。
6. 静态校验时确认：镜像大小、节数量、新节 RVA/原始偏移、以及旧 4 字节常量（`0x1005340` 等）**零残留**。

## 五、棋盘字节编码（实测）

通过 `ReadProcessMemory` dump 得到：

| 字节 | 含义 |
|---|---|
| `0x0F` | 未打开、非雷 |
| `0x8F` | 雷（`0x80 \| 0x0F`） |
| `0x40 \| n` | 已打开，周围 n 颗雷（n=0..8） |
| `0x10` | 边界格（棋盘外一圈） |
| `0x0E` | 已插旗（低 5 位为 `0x0E`） |

重要结论：**邻雷计数只有在格子被翻开时才写入**。未打开格统一是 `0x0F`/`0x8F`，所以不能“点前扫描内存找 0 格”，只能靠已知雷位避开雷后逐格点击来触发洪水展开。

## 六、运行时验证注意事项

1. **雷在开局（reset）就已布置，没有“首点安全”。** dump 显示点击前已有 999 个 `0x8F`。因此验证脚本先读内存雷位，只点非雷格。
2. **扫雷自身把雷数下限钳到 10。** 注册表写 `Mines=1` 会被改成 10，验证时不要用小于 10 的雷数作为期望值；上限仍是 999。
3. **配置在 `HKCU\Software\Microsoft\winmine`。** `Difficulty=3` 表示自定义，宽高在启动时读取；脚本会先备份全部值、结束时恢复，避免污染用户配置。
4. **模拟点击坐标**：客户区第一格中心为 `(12+8, 55+8)`，格宽高 16，第 `(x,y)` 格中心 = `(12 + (x-1)*16 + 8, 55 + (y-1)*16 + 8)`。用 `SendMessage` 发 `WM_MOUSEMOVE` → `WM_LBUTTONDOWN` → `WM_LBUTTONUP`，消息是同步处理，返回后即可读内存。
5. **读内存需要权限**：`OpenProcess(PROCESS_VM_READ | PROCESS_QUERY_INFORMATION)`（`0x10 | 0x400`）。
6. **窗口查找**：按进程 PID 枚举可见顶层窗口，选客户区面积最大者；不要只按标题“扫雷”找，避免误匹配。
7. **洪水完整性判定**：对每个已打开且计数为 0 的格子，其 8 邻域必须是“已打开”或“已插旗”，否则说明 BFS 队列溢出导致漏格。
8. **窗口可能超出屏幕**：62×62 窗口为 `1012×1055`，1080p 屏上底部会被任务栏遮住，但 `SendMessage` 坐标点击与离屏渲染仍正常。

## 七、方案 B 实测结果

| 用例 | 结果 |
|---|---|
| 9×9 / 10 | 通过，全部解开 |
| 30×24 / 120 | 通过，594/600 已开，0 漏格 |
| 62×62 / 10 | 通过，**一次点击洪水展开全部 3834 个非雷格，0 漏格** |
| 60×60 / 999 | 通过，运行正常，0 漏格，进程存活 |
| 62×62 / 999 | 通过，达到补丁上限，0 漏格，进程存活 |

`62×62 / 10` 是队列压力最大的用例：127 格容量足以完成全盘洪水展开，说明 `.bigbrd` 节内队列搬家与容量扩展正确。

## 八、已知限制

- 雷数上限仍为 999（未改 `0x3E7`）。
- 窗口高度 1055px，超高分辨率屏幕体验更好。
- 队列容量 127 对 62×62 已验证足够，但对更大棋盘需要重新评估。
- **B 只修了注册表加载路径的钳制。** 手工在“自定义”对话框里输入 62，仍会被另一条路径钳回 24/30，详见第九节第 5 条；通过注册表启动则不受影响。

## 九、方案 C 调研结论（暂不实施，2026-10-31）

### 9.1 结论

方案 C 的本质不是“把内存里的宽高改大”。宽高本身是 32 位 DWORD，数值范围完全够用；真正的限制来自三处：

1. 行索引用的是 `shl`，**步长只能是 2 的幂**；
2. 跨行加减、队列回绕、部分钳制用的是 **imm8（1 字节立即数）**，超过 ±127 就必须改指令长度；
3. 程序无重定位表、无 ASLR、`.text` 内无可用代码洞，**任何指令变长都会破坏后续所有硬编码的相对跳转**。

B（32→64）能全部等长替换，是因为 `64` 仍是 2 的幂、`0x40` 仍在 imm8 范围内。C 会同时击穿这两条，因此暂不实施。

### 9.2 已核实的指令编码

**跨行步长 10 处（全部 3 字节 `83 xx 20`，imm8）：**

| 地址 | 原字节 | 指令 |
|---|---|---|
| `0x100271D` | `83 c3 20` | `add ebx, 0x20` |
| `0x1002F2A` | `83 ea 20` | `sub edx, 0x20` |
| `0x1002F2D` | `83 e8 20` | `sub eax, 0x20` |
| `0x1002F74` | `83 c2 20` | `add edx, 0x20` |
| `0x1002FCF` | `83 c7 20` | `add edi, 0x20` |
| `0x100315B` | `83 c2 20` | `add edx, 0x20` |
| `0x1003309` | `83 c6 20` | `add esi, 0x20` |
| `0x1003343` | `83 c6 20` | `add esi, 0x20` |
| `0x1003563` | `83 c7 20` | `add edi, 0x20` |
| `0x1003642` | `83 c6 20` | `add esi, 0x20` |

- 步长 128 时 `0x80` 会被符号扩展成 −128，必须用 imm32：`81 c3 80 00 00 00`（6 字节），**每处 +3 字节**。
- 一个较小的替代方案是 `add reg,0x7F` + `inc reg`（4 字节），每处只 +1 字节，但仍会跨过指令边界，同样需要处理重定位。
- 22 处 `shl r32,5` 改成 `shl r32,7`（128）或 `shl r32,8`（256）都是等长替换，没有问题。

**洪水队列回绕 2 处（3 字节 imm8，只做相等比较）：**

- `0x100306C`：`83 f8 64` = `cmp eax, 0x64`
- `0x1003103`：`83 fb 64` = `cmp ebx, 0x64`

imm8 能表示的最大非负值只有 127，所以“免费”扩容上限是 `0xFF`（255 格）。超过 255 必须改成 `cmp reg, imm32`（6 字节），同样变长。

**宽高钳制入口 4 处（`6A imm8` = `push imm8`，符号扩展）：**

| 地址 | 原值 | 含义 |
|---|---|---|
| `0x10015ED` | `push 0x18` | 自定义对话框高度上限 24 |
| `0x10015FC` | `push 0x1E` | 自定义对话框宽度上限 30 |
| `0x1002BEB` | `push 0x19` | 注册表加载高度上限 25 |
| `0x1002BF9` | `push 0x1E` | 注册表加载宽度上限 30 |

- 126 可以用 `push 0x7E`（126，仍在 imm8 正数范围内）。
- 254 要用 `push 0xFE`，会被符号扩展成 −2，**必须改 `push imm32`（5 字节）或改写判定逻辑**。
- 注意还有一套未在 B 中修改的钳制：`0x1003B69 push 0x19`、`0x1003B77 push 0x1E`，调用的是同一族钳制助手 `0x1003A12`，应属于对话框确认路径。B 因为走注册表所以没暴露，做 C 必须一起审计。
- 其余 `push 0x18/0x1E` 经上下文核对不是尺寸钳制（`0x1002544`、`0x1002546`、`0x10027DC`、`0x10028F5`、`0x10028FA`、`0x10028FC`、`0x1002D09`、`0x1003C78` 多为控件 ID、绘制参数或时间参数）。

**雷数上限（等长可改，但 C1 不需要）：**

- `0x1001620`：`mov ecx, 0x3E7`（999）
- `0x1002C22`：`mov esi, 0x3E7`（999）

两者都是 imm32，改大是等长的。但界面计数器只有 3 位，超过 999 显示会异常；126×126 用 999 雷密度约 6%，没有必要改。

**16px 格子相关位置（改 8px 时需要一起动，但位图素材是 16px）：**

| 地址 | 指令 | 用途 |
|---|---|---|
| `0x10019E0`、`0x10019F0` | `shl eax, 4` | 窗口尺寸 `W*16` / `H*16` |
| `0x10020A2`、`0x10020AD`、`0x10020ED`、`0x10020F0`、`0x100217D`、`0x1002188` | `sar eax/ecx, 4` | 鼠标坐标 → 格子坐标 |
| `0x100267D`、`0x1002687` | `shl ecx/eax, 4` | 绘制坐标 |
| `0x1002706`、`0x1002719` | `add dword ptr [ebp-4/-8], 0x10` | 绘制循环步进 |

窗口尺寸公式：`W*16+0x18`、`H*16+0x43`。

### 9.3 B / C1 / C2 对照

| 项目 | B：62×62（已完成） | C1：126×126 | C2：254×254 |
|---|---|---|---|
| 步长 | 64，`shl 6` 等长 | 128，`shl 7` 等长 | 256，`shl 8` 等长 |
| 跨行加减 | `0x40` imm8 等长 | `0x80` 需 imm32，10 处变长 | `0x100` 需 imm32，10 处变长 |
| 棋盘数组 | `0x1000` | `0x4000` | `0x10000` |
| 宽高钳制 | `0x3E` imm8 | `0x7E` imm8，刚好可用 | `0xFE` 符号扩展，需变长 |
| 队列容量 | 127 | 最多 255（够不够未知） | 必须 >255，一定变长 |
| 窗口尺寸 | 1012×1055 | 2040×2083 | 4088×4131 |
| 人工可玩 | 勉强 | 1080p 下不行 | 完全不行 |

因为步长必须为 2 的幂，当前代码结构能到的宽度是 **62 / 126 / 254 / 510**，不是任意值。若要任意宽度，必须把 22 处 `shl` 改成 `imul`，属于更大的改造。

### 9.4 风险清单

**确定会卡住（必须动代码，不是改值）：**

1. 10 处行步长需要变长；trampoline/整函数搬迁时任何相对跳转重算错误，都会导致崩溃或静默错位（格子写到错误行）。
2. 队列容量超过 255 时，两处 `cmp imm8` 必须变长。
3. 254 的 `push imm8` 符号扩展问题。

**需要实测，静态分析无法保证：**

4. 126×126 的洪水前沿是否 ≤255。62×62 全盘展开用 127 通过，但 62 通过不代表 126 通过。
5. `.data` 中启动期预计算表/位图（`0x1005960`、`0x1005a60` 等）尚未证明对 >62 的尺寸安全。

**工作量最大且与内存无关：**

6. UI：16px 格子 + `W*16` 窗口；126 已是 2040×2083，超出 1080p。改 8px 只改移位是等长的，但数字/雷/红旗位图按 16px 绘制会重叠；需要重画素材或实现滚动视口。

### 9.5 若将来恢复 C 的建议顺序

1. **C1 可行性预检**：先做 126×126 的临时补丁，只验证“尺寸、雷数、点击、洪水漏格”，不碰 UI；若队列 255 不够或出现静默错位，再评估是否投入 trampoline 工程量。
2. **C1 自动化版**：保留 16px、接受超屏窗口，用 `SendMessage` 验证；这一步才能证明 C 路线可行。
3. **C1 人工可玩版**：再决定 8px 还是滚动视口，属于 UI 工程。
4. **C2 / 真正无限**：需要队列变长、254 钳制变长；真正无限还要把移位索引改成乘法索引并做动态分配，基本等于重写，不建议作为目标。

验收标准需提前确定：**“自动化能跑”还是“人也能玩”**。后者会显著扩大范围。
