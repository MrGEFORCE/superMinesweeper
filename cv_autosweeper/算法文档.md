# CV 自动扫雷算法文档

本文档对应 [cv_autosweeper.py](./cv_autosweeper.py)，说明整体流程、识别方法和求解 / 猜雷算法。

---

## 1. 总体流程

```
启动 / 附着窗口
   │
   ├─ 枚举顶层窗口，按类名“扫雷”或标题匹配，取客户区最大的那个
   │   （若客户区 0×0，判定为最小化，直接报错退出）
   │
   └─ 每一局：
        1. 首点：opened==0 且 flags==0 时，直接点棋盘中心（XP 首点必安全）
        2. 循环：
             PrintWindow 后台截图
               → 颜色直方图逐格分类
               → LED 三位数字识别剩余雷数
               → 状态汇总（未知格 / 旗 / 已开 / 是否踩雷）
               → 踩雷 / 胜利 / 异常 判定
               → 确定解推导 (单格 + 子集 + 全局雷数)
               → 有解：右键标雷、左键开安全格，继续
               → 无解：概率估计 + 选最安全格，点一下，继续
        3. 下一局用 WM_COMMAND 510（菜单“开局 F2”）重开
```

所有对窗口的操作都是后台消息，不需要真实鼠标 / 键盘，窗口被遮挡也可以跑。

## 2. 窗口与几何

| 量 | 表达式 | 说明 |
|---|---|---|
| 客户区宽 | `client_w = w*16 + 20` | 左右各 2px 边框 + 12px 棋盘左边界 + 4px 余量 |
| 客户区高 | `client_h = h*16 + 63` | 顶部计分板 + 棋盘 |
| 棋盘原点 | `(12, 55)` | 第一格左上角在客户区中的坐标 |
| 格子 | `16 × 16` px | |
| 反推宽 | `w = (client_w - 20) // 16` | |
| 反推高 | `h = (client_h - 63) // 16` | |

点击第 `(x, y)` 格（0 基）：

```
px = 12 + x*16 + 8
py = 55 + y*16 + 8
lParam = (py << 16) | px
```

与 `memory_autosweeper` 的几何常量完全一致。

## 3. 后台截图

```python
GetClientRect(hwnd)                  # 客户区尺寸
GetDC → CreateCompatibleDC → CreateCompatibleBitmap
PrintWindow(hwnd, mdc, PW_CLIENTONLY | PW_RENDERFULLCONTENT)  # flags = 0x3
GetDIBits(..., biBitCount=32, biHeight=-ch)                    # top-down
```

- `PrintWindow` 由窗口自己绘制到内存 DC，与窗口是否在前台、是否被遮挡无关。
- 截图后统一释放 GDI 对象（`SelectObject` 还原、`DeleteObject`、`DeleteDC`、`ReleaseDC`）。
- 像素格式为 BGR，返回前翻转为 RGB。
- 最小化时 `GetClientRect` 返回 0×0，`PrintWindow` 也拿不到内容，因此直接报错，不做兜底。

后台点击：

```python
SendMessageTimeoutW(hwnd, WM_MOUSEMOVE, ..., SMTO_ABORTIFHUNG, 2000ms)
SendMessageTimeoutW(hwnd, WM_LBUTTONDOWN / UP 或 WM_RBUTTONDOWN / UP, ...)
```

用超时版本是为了避免对话类窗口（例如胜利后弹框）把线程挂死；返回 0 判为“窗口无响应”。

## 4. 图像识别

### 4.1 格子分类

把棋盘区域 reshape 成 `(h, 16, w, 16, 3)`，对 10 种关键颜色逐格计数：

```
white(255,255,255) g192(192,192,192) g128(128,128,128) black(0,0,0)
red(255,0,0)       maroon(128,0,0)   blue(0,0,255)      navy(0,0,128)
green(0,128,0)     teal(0,128,128)
```

XP 扫雷只用这些纯色，因此用“精确等值 + 计数”比阈值匹配稳定得多。

判定顺序（决策树）：

```
white >= 20                    → 有白色高光，属于“未开类”
    red >= 8  且 black >= 8    → 旗
    black >= 8                 → 问号
    否则                       → 未开
red >= 60 且 black >= 30       → 踩中的雷（大片红底）
blue >= 15                     → 1
green >= 20                    → 2
red >= 20                      → 3
navy >= 20                     → 4
maroon >= 25                   → 5
teal >= 25                     → 6
black >= 20                    → 7
g128 >= 70                     → 8
否则                           → 0
```

阈值来自实机逐格统计（见下表，单位：16×16 区域内的像素个数）：

| 格子 | 主要颜色计数 |
|---|---|
| 未开 | white 54, g192 148, g128 54 |
| 旗 | black 22, g128 54, g192 109, red 17, white 54 |
| 问号 | black 24, g128 54, g192 124, white 54 |
| 0 | g192 225, g128 31 |
| 1 | blue 40, g128 31, g192 185 |
| 2 | green 65, g192 160 |
| 3 | red 62, g192 163 |
| 4 | navy 56, g192 169 |
| 5 | maroon 70, g192 155 |
| 6 | teal 72, g192 153 |
| 7 | black 44, g192 181, g128 31 |
| 8 | g192 149, g128 107 |
| 踩中的雷 | red ≈144, black ≈77, g128 31, white 4 |

已知失真：**踩雷后**，未点开的雷会显示成黑色雷图形，会被读成 7。这只会发生在已经判负的帧，不影响正常流程。

### 4.2 顶部 LED 剩余雷数

扫雷顶部计数器是 7 段红色 LED，三位数字。位置与尺寸：

```
每位 x0 = 17 + 13*i   (i = 0,1,2)
y  = 14,  宽 13, 高 26
```

识别方法：

1. 取该位 13×26 区域，按红色掩码 `R>200 且 G<70 且 B<70` 得到 13×26 布尔图。
2. 与 0-9 的模板（同样尺寸、`np.packbits` + base64 内嵌）逐位异或，取差异像素数最小者。
3. 最小差异 > 14 视为识别失败，返回 `None`。

模板是实机采集的（内存里写 LED 位图值 + 强制重绘后截图），`123` 实测 diff=0。

用途：

- 全局雷数约束（见 5.3）；
- 胜利判定：不再有未知格时，要求 LED 归零；
- 奇数情况：雷数 > 999 或为负（显示负号）时识别失败，此时求解器退化为“不带全局约束”的模式。

## 5. 求解器

### 5.1 约束的定义

对每个**已开**格 `(x, y)`，值为 `n`，它的 8 邻域中：

- 旗数 `flags`
- 本轮已推导出、但还没真正右键的雷数 `known_mine`
- 剩余未知格集合 `U`（排除旗、排除已推导出的安全格与雷）

约束为：

```
r = n - flags - known_mine        # 该邻域里还必须有多少颗雷
```

合法性检查：`0 <= r <= len(U)`，否则视为读数矛盾（识别错误）直接返回。

### 5.2 单格规则

```
r == 0        →  U 全部安全
r == len(U)   →  U 全部是雷
```

### 5.3 全局雷数规则

LED 给的是“还没插旗的雷数” `remaining`。但本轮新推导出的雷 `mine` 还没有真正右键，LED 尚未减掉它们，所以：

```
eff = remaining - len(mine)
```

- `eff == 0` → 所有未知格安全；
- `eff == len(unknown)` → 所有未知格是雷。

> 这是早期版本一个真实 bug 的修复点：直接用 `remaining` 会导致同一格既被判安全又被判雷。

### 5.4 子集规则

对约束对 `(U1, r1)`、`(U2, r2)`，若 `U1 ⊆ U2`：

```
diff = U2 - U1,  rd = r2 - r1
rd == 0            →  diff 全部安全
rd == len(diff)    →  diff 全部是雷
```

只比较中心切比雪夫距离 ≤ 2 的约束对（远处约束几乎不可能有包含关系），避免 O(n²) 全量比较。

### 5.5 迭代与收敛

```
最多 40 轮：
  重建全部约束
  应用全局规则
  应用单格规则
  若本轮无新增：
      应用子集规则
      仍无新增 → break
```

所有新增的 safe / mine 都做差集去重（`add = U - safe - mine`），最后若 `safe ∩ mine` 非空，判定矛盾。

返回值：`(safe, mine, cons)`。

### 5.6 前沿连通分量

把“出现在某个约束 U 里的未知格”定义为**前沿**，其余为**非前沿**。

按“共享同一约束的格子”做并查集，把前沿切成若干连通分量。每个分量内部各约束互相耦合，但分量之间相互独立（只通过全局雷数 `remaining` 关联）。

空约束（`U` 为空）在分组前直接剔除。

## 6. 概率估计与猜雷

当 5.x 推不出任何确定解时，进入概率估计。

### 6.1 分量穷举

对每个分量做 DFS 枚举所有合法布雷方案：

- 变量顺序：按“参与的约束数”从多到少排序（约束多的格子先定，剪枝更早）。
- 剪枝：记录每个约束“已用雷数”和“剩余未赋值格数”，一旦 `left < 0` 或 `left > left_cells` 立即回溯。
- 记录：
  - `dist[k]`：该分量恰好 `k` 颗雷的合法方案数；
  - `per_cell[c][k]`：其中格子 `c` 为雷的方案数。
- 节点预算 `ENUM_BUDGET = 1,500,000`；分量大小上限 `MAX_COMP = 32`。超限 → 该分量放弃精确枚举。

### 6.2 全局一致性加权

设非前沿格数 `n_nf`，剩余雷数 `remaining`。对分量总雷数 `k` 定义组合权重：

```
W(k) = C(n_nf, remaining - k)     # 若 remaining-k 越界则 0
```

把所有分量的 `dist` 做卷积，得到全体前沿的雷数分布 `G_all`：

```
G_all = dist_1 * dist_2 * ... * dist_m        （多项式卷积）
Z     = Σ_k G_all[k] * W(k)
E_frontier = Σ_k k * G_all[k] * W(k) / Z
```

对第 `i` 个分量，其余分量的卷积记为 `G_other`，则该分量恰好 `k` 颗雷的边缘权重：

```
w_i(k) = Σ_t G_other[t] * W(k + t)
```

于是：

```
P(格子 c 是雷) = Σ_k per_cell_i[c][k] * w_i(k) / Z
```

非前沿格统一概率：

```
P_nf = (remaining - E_frontier) / n_nf        （截断到 [0,1]）
```

这套加权保证：**所有格子的概率与“全局恰好 `remaining` 颗雷”自洽**，各分量不是各自归一化后拼起来的。

### 6.3 精确的“0%”

由于枚举是完备的，`P(c)=0` 意味着该格在所有符合全局雷数约束的布局里都不可能是雷——这是比单格 / 子集规则更强的确定性推理。日志里 `雷概率 0.0%` 的“猜测”实际上是确定安全格。

### 6.4 超限时的退化估计

任一分量超限（>32 格或超预算）时，整体退化为“约束密度均值”：

```
p(c) = mean over 覆盖 c 的约束 ( r / |U| )
E_frontier ≈ Σ p(c)        （粗略，可能高估）
P_nf = (remaining - E_frontier) / n_nf
```

这一步只用于超大棋盘的中局，精度明显低于 6.2。

### 6.5 选格策略

```
候选 = 前沿格 ∪ 非前沿格
key  = (round(P, 6), 前沿优先=0 / 非前沿=1, y, x)
取 key 最小的格子
```

即：优先挑雷概率最低的格；概率相同时优先前沿格（翻它能立刻产生新约束），再按行列序。

`--no-guess` 模式下不点，直接报告卡住和当前最小概率。

## 7. 一局的判定

| 状态 | 条件 | 结果 |
|---|---|---|
| 踩雷 | 出现 `HIT` 格（大片红底） | 负 |
| 胜利 | 无未知格/问号，且 LED 剩余雷数为 0 | 胜 |
| 异常 | 无未知格但 LED 剩余雷数 ≠ 0 | 视为识别错误，停止 |
| 卡住 | 无确定解且 `--no-guess` | 停止 |

XP 胜利时会自动给所有雷插旗，所以“全部格子已开或已插旗 + LED 归零”是可靠判据；只判“没有未知格”会在识别出错时误判胜利（早期版本踩过这个坑）。

重开用 `WM_COMMAND 510`。实测：胜利后点笑脸会让窗口线程挂起且不重开，`WM_KEYDOWN(F2)` 也不走窗口过程，只有菜单命令可靠。

## 8. 复杂度与性能

| 环节 | 复杂度 | 实测 |
|---|---|---|
| 截图 | O(w·h) 像素拷贝 | 62×62 约 1M 像素，可忽略 |
| 分类 | 10 次全区域比较 + 每格常数次判断 | numpy 向量化，毫秒级 |
| 推导 | 最多 40 轮 × O(格数×8) | 毫秒级 |
| 分量枚举 | 最坏 2^n，剪枝后通常 ≪ 预算 | 30 格分量最慢约 44ms |
| 整局 | 每次点击后全量重算 | 9×9 约 0.7s/局；62×62/500 约 12s/局（1600+ 次点击） |

> 每次点击后都重新截图、重新识别、重新推导。这样实现简单，并且天然免疫漏识别；大棋盘靠 `--delay 0.002` 把点击间隔压到最小。

## 9. 实测结果

| 棋盘 | 局数 | 胜率 |
|---|---|---|
| 9×9 / 10 | 20 | 90% |
| 16×16 / 40 | 20 | 65% |
| 30×16 / 99 | 10 | 50% |
| 62×62 / 500（补丁版） | 3 | 100% |

正确性另用内存真值脚本逐格校验（校验项：识别结果、每条约束的 `r`、推导出的 safe / mine、胜利局的实际开格数和旗数），全部一致。

## 10. 已知限制

1. **窗口不能最小化**：客户区 0×0 时无法截图。
2. **雷数显示为负**：LED 出现负号时 OCR 失败，全局雷数约束失效，仅剩局部规则与概率猜测。
3. **猜雷策略未做信息增益**：同概率时只按“前沿优先 + 行列序”挑，没有评估“翻开后能解锁多少约束”的期望收益。
4. **超大前沿分量退化为密度均值**：精度低于精确枚举，主要出现在大棋盘高雷密度局。
5. **踩雷后的画面**：未点开的雷是黑色图形，会被读成 7；只在判负帧出现，不影响流程。
